## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Build habit management and tracking on the existing `/calendar` page with a top-level switch between the normal Google Calendar view and a dedicated Habit view. The Habit view follows a full month grid similar to the provided reference: each scheduled habit appears as a compact colored checkbox item inside every applicable day cell, with per-day completion progress. Habit creation/editing/deletion remains available from this page.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
## Incremental implementation plan
1. Add a persisted top-level Calendar/Habits mode switch to the existing `/calendar` page, preserving the normal calendar's month/week controls and Google actions only in Calendar mode.
2. Build the initial dedicated Habit month-grid shell using the same date state/navigation and Atlas styling, with a clear empty state and Add habit affordance; pause for user visual review.
3. Add habit API types/client/hooks and management form/list.
4. Render only scheduled habits in each date cell and wire optimistic completion toggles with rollback.
5. Add progress/loading/error states, focused tests, and final verification.

### Habit table view
- Add a persisted Month/Table sub-view toggle inside Habit mode.
- The table view will show one row per date for the selected month, a progress summary, one checkbox column per active habit, and a completed count, reusing the same schedule filtering and completion state as the month grid.
- Build the table shell during the next visual increment before API wiring so both layouts can be reviewed together.

### Completion rendering correction
- Wire completions now so both Month and Table views render scheduled habits and interactive checkboxes instead of placeholders.
- Limit Table view to 10 dates per page with pagination controls and reset/clamp pagination when the month changes.
- Add a New page row/action that opens the habit form with that row's date prefilled; a new date row derives day/date automatically and starts at 0% until completions exist.
- Share schedule filtering and completion calculations between both views so daily/weekly/start/end rules remain consistent.

### User review corrections
- Ensure Month and Table consume the same `useHabitCompletions` state rather than separate instances so toggles remain visible across view switches.
- Replace bright management/table separators with the subtle border token.
- Change Table semantics from an auto-generated month matrix to user-created date rows: no empty dates/columns are generated automatically; New page explicitly adds/selects a date row, and only that row shows schedule-derived habit checkboxes and progress.
- Keep Month view schedule-based, but do not populate the Table with dates until the user adds them.

### Confirmed explicit-day model
- Remove recurrence/start/end controls and schedule filtering from habit UI.
- Persist date rows through backend `habit_days`; no session-only date list.
- Rename New page to New. Clicking it creates today's row automatically; if today exists the API returns it without duplication.
- Both Table and Month render only explicit habit-day rows. Every row/card contains all active habits, with progress derived from completions.

### Viewport-fit month grid
- Replace fixed minimum day-cell heights with a viewport-aware grid height.
- Divide the available height evenly across all six calendar rows and keep overflow inside individual day cells when habit content exceeds available space.
- Preserve normal page scrolling as a fallback on short/mobile viewports.

### Collapsible habit management
- Add a persisted collapsed state to the habit management panel with a compact header-only mode.
- Default to collapsed once habits exist so the calendar receives most of the viewport; keep Add habit accessible from the header and the global action.
- Recalculate the month grid height for collapsed versus expanded panel instead of forcing the same undersized height in both states.
