## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Build the habits data layer and CRUD API on the Go backend. This is fully independent of the Google Calendar work — can be built and tested standalone.

**Data model:**
- `habits` table: `id` (text PK), `name` (text), `description` (text, optional), `color` (text, optional — for UI indicator), `icon` (text, optional — Lucide icon name), `created_at` (timestamp), `archived_at` (timestamp nullable — soft delete for history preservation)
- `habit_completions` table: `id` (text PK), `habit_id` (text FK → habits.id), `date` (date — the day the habit was completed), `completed_at` (timestamp). Unique constraint on `(habit_id, date)` so a habit can be toggled only once per day.

**Endpoints:**
- `GET /api/habits` — list user's habits (exclude archived)
- `POST /api/habits` — create
- `PATCH /api/habits/{habitId}` — update
- `DELETE /api/habits/{habitId}` — soft-delete (set `archived_at`)
- `GET /api/habits/completions?start=&end=` — list completions in range (for rendering the calendar checkboxes)
- `POST /api/habits/completions` — toggle completion for `{ habitId, date }` (idempotent: if exists, delete; if not, insert)
- `GET /api/habits/{habitId}/completions?start=&end=` — single-habit history (for any future streak/percentage calc; not required for v1 but cheap to add now)

**Architecture notes for implementer:**
- Storage follows the existing SQLite pattern in `server/internal/store/`. Same single-user model as the smartboard panels — no user/auth table needed unless the codebase adds one later.
- Follow the smartboard store/handler/service pattern: `server/internal/store/habit.go`, `server/internal/services/habit.go`, `server/internal/api/habit/habit.go`.
- Register routes in `server/cmd/server/main.go` following the existing `smartBoardAPI` registration pattern.

**Can be worked in parallel with LOS-012.2 (backend Google sync) — no dependency between them.**
