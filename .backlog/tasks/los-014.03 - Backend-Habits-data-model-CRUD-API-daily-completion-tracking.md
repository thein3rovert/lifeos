## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Build the habits data layer and CRUD API on the Go backend. This is fully independent of the Google Calendar work — can be built and tested standalone.

**Data model:**
- `habits` table: `id` (text PK), `name` (text), `description` (text, optional), `color` (text, optional — for UI indicator), `icon` (text, optional — Lucide icon name), `created_at` (timestamp), `archived_at` (timestamp nullable — soft delete for history preservation)
- `habit_completions` table: `id` (text PK), `habit_id` (text FK → habits.id), `date` (date — the day the habit was completed), `completed_at` (timestamp). Unique constraint on `(habit_id, date)` so a habit can be toggled only once per day.

**Endpoints:**
- `GET /api/habits` — list user's habits (exclude archived)
- `POST /api/habits` — create
- `PATCH /api/habits/{habitId}` — update
- `DELETE /api/habits/{habitId}` — soft-delete (set `archived_at`)
- `GET /api/habits/completions?start=&end=` — list completions in range (for rendering the calendar checkboxes)
- `POST /api/habits/completions` — toggle completion for `{ habitId, date }` (idempotent: if exists, delete; if not, insert)
- `GET /api/habits/{habitId}/completions?start=&end=` — single-habit history (for any future streak/percentage calc; not required for v1 but cheap to add now)

**Architecture notes for implementer:**
- Storage follows the existing SQLite pattern in `server/internal/store/`. Same single-user model as the smartboard panels — no user/auth table needed unless the codebase adds one later.
- Follow the smartboard store/handler/service pattern: `server/internal/store/habit.go`, `server/internal/services/habit.go`, `server/internal/api/habit/habit.go`.
- Register routes in `server/cmd/server/main.go` following the existing `smartBoardAPI` registration pattern.

**Can be worked in parallel with LOS-012.2 (backend Google sync) — no dependency between them.**

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
## Implementation plan
1. Add centralized SQLite migrations for `habits` and `habit_completions`, including soft-delete metadata and a unique habit/date completion constraint.
2. Add habit models and a SQL store supporting active-habit CRUD, soft deletion, inclusive completion-range queries, and atomic idempotent completion toggles.
3. Add a habit service for input/date validation and stable ID generation, preserving explicit optional-field updates.
4. Add JSON HTTP handlers for the requested CRUD, range, toggle, and per-habit completion endpoints and register them in the server mux.
5. Add store/service/handler tests, then run Go tests, build, and vet before finalizing.

### Recurring habit schema adjustment
- Extend `habits` with explicit schedule fields: recurrence frequency (`daily` or `weekly`), selected weekday tokens for weekly schedules, required start date, and optional end date.
- Keep `habit_completions` as actual checked dates, independent from the schedule definition.
- Add idempotent ALTER migrations for any local database that already created the first schema version and extend the migration test to verify the new columns.

### Corrected habit domain model
- Remove schedule semantics from habit definitions; habits are reusable checkbox definitions only.
- Add a `habit_days` table with one unique date per tracking row. `POST /api/habit-days` creates today's/requested date idempotently and returns the existing row when already present.
- Completion records remain `(habit_id, date)` and are displayed only for explicit habit-day rows.
- Keep legacy schedule columns physically present for SQLite compatibility but stop requiring or exposing them in current domain/API behavior.
