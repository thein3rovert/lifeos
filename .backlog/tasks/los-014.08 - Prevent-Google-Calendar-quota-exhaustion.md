## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
LifeOS can issue many duplicate event-list requests and repeatedly fetch recurring-series master metadata after calendar changes, causing Google Calendar API 403 RATE_LIMIT_EXCEEDED errors at the per-user queries-per-minute limit. Reduce request amplification while keeping event and recurrence information fresh.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Concurrent identical event-range requests are coalesced so they do not trigger duplicate Google API calls
- [x] #2 Recurring-series master metadata is cached across event requests with safe invalidation after relevant mutations
- [x] #3 Repeated frontend refresh triggers for the same visible range are deduplicated or throttled
- [x] #4 Google rate-limit errors return a stable API code and the frontend shows a helpful retry-later message
- [x] #5 Existing recurrence metadata event updates and stale-response protection remain functional
- [x] #6 Focused backend and frontend tests plus production builds pass
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
## Plan
1. Inspect frontend effect/refresh behavior and backend recurrence enrichment to identify duplicate calls and suitable cache boundaries.
2. Add a concurrency-safe backend cache for recurring master metadata and coalesce identical in-flight range requests, invalidating caches after create/update/delete/disconnect.
3. Add frontend same-range request coalescing and a short freshness window so Strict Mode/effect churn and immediate post-mutation refreshes reuse current work.
4. Classify Google rate-limit responses into a stable API response and render a clear retry-later state.
5. Add focused concurrency/cache/error tests and run backend/frontend verification.
<!-- SECTION:PLAN:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implemented quota protection after logs confirmed Google Calendar 403 RATE_LIMIT_EXCEEDED. Backend now coalesces identical in-flight range requests, caches/coalesces recurring master metadata for five minutes, returns deep copies, and invalidates safely after calendar mutations/disconnect. Google rate limits map to stable HTTP 429 code `google_calendar_rate_limited`. Frontend coalesces identical in-flight requests across hook instances/Strict Mode, reuses successful same-range data for five seconds, and supports forced post-mutation refresh without stale optimistic data. Rate-limit failures show a retry-later message. Verification passed: race-enabled backend service/handler tests, full Go tests/vet, 27 calendar frontend tests, focused Biome, production build, and whitespace validation.
<!-- SECTION:NOTES:END -->
